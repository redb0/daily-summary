## Тестирование

### Добавляйте тест, только если на этом изменении ещё не падает ничего другого

Прежде чем писать новый тест, спросите себя: что уже станет «красным», если изменение неверное? Другой тест в наборе или `mypy`, прогоняемый по коду проекта, который уже проходит по этому пути. Если ошибку уже что-то ловит — не добавляйте ещё один тест. Тикет с требованием «тест на каждый случай» это правило не отменяет: вместо теста, который просто повторяет существующую проверку, укажите, какая уже имеющаяся проверка покрывает остальное. Никогда не фиксируйте в тестах поведение языка или стандартной библиотеки, за которое проект не отвечает (например, что `NamedTuple` распаковывается или что `==` работает для кортежей).

### Одно сравнение на одно поведение

Когда тест проверяет одно значение с разных сторон — поля кортежа, несколько ключей словаря, длину и элемент — соберите ожидаемую структуру из матчеров `dirty-equals` и сравните один раз. Тогда при падении выводится вся структура целиком, а тест читается как единое утверждение о поведении:

```python
# Claimed entries come first, with their previous deliveries and idle time
assert received[:2] == [
    ("pending_message", IsInt(ge=1), IsInt(ge=100)),
    ("new_message", 0, 0),
]

assert snapshot == IsPartialDict(
    {
        "delivery_counts": HasLen(size),
        "idle_times": HasLen(size),
    }
)
```

Цепочка `assert x[0] ...`, `assert x[1] ...` или цикл с флагом `found` — это та же структура, растянутая по одному полю за раз: сверните её в одно сравнение. `IsPartialDict` принимает словарный литерал, поэтому ключи через точку и значения enum читаются так же, как конфиг, который они отражают. Сравнение, которое и так упадёт при отсутствующей доставке, самодостаточно; стоящий перед ним `assert event.is_set()` больше ничего не добавляет.
